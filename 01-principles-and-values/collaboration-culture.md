# Collaboration Culture

How we work together as volunteers at Better.sg.

## Our Foundation

Better.sg is a **volunteer-run charity** with over 2,000+ members. We're built on the understanding that everyone has other commitments - jobs, families, studies - and that's not just okay, it's expected. Our collaboration culture reflects this reality.

---

## Core Collaboration Principles

### Async-First Communication 📬

**What it means:**
- Default to asynchronous communication (Slack, GitHub, email)
- Don't expect immediate responses
- Document decisions so others can catch up
- Use threads to keep conversations organized

**Why it matters:**
- Respects everyone's time and schedule
- Enables global collaboration across timezones
- Creates a record of decisions and discussions
- Reduces pressure and burnout

**In practice:**
- Write comprehensive Slack messages with context
- Use GitHub issues/PRs for technical discussions
- Update project status in written form
- Schedule meetings only when truly necessary
- Record meetings for those who can't attend

### Meetings Are Optional 📋

**What it means:**
- Meetings should be the exception, not the norm
- Always have a clear agenda and goal
- Make recordings and notes available
- No guilt for not attending

**When to have meetings:**
- Kickoff for new projects
- Complex technical discussions requiring back-and-forth
- Team bonding and community building
- Quarterly retrospectives

**How to run good meetings:**
- Share agenda 24 hours in advance
- Start and end on time (max 1 hour)
- Assign a note-taker
- Share summary and action items after
- Record for those who couldn't make it

## Communication Channels

### Slack 💬

**Primary channels:**
- `#general` - Community announcements and discussions
- `#project-[name]` - Project-specific channels
- `#general` - Looking for volunteers
- `#engineering` - Technical questions and learning
- `#random` - Off-topic chat and community bonding

**Best practices:**
- Use threads to keep conversations organized
- @mention only when you need someone's attention
- Use #channel mentions sparingly (emergencies only)
- Check pinned messages for important info
- Set your status to reflect availability
- Use Do Not Disturb during your off hours

### GitHub 🐱

**Primary uses:**
- Issues for bug reports and feature requests
- Pull Requests for code review
- Discussions for architectural decisions
- Project boards for tracking work

**Best practices:**
- Write clear issue descriptions with context
- Link related issues and PRs
- Use labels to categorize work
- Assign yourself to issues you're working on
- Request reviews explicitly (don't assume)
- Be thorough but kind in code reviews

### Email 📧

**Use for:**
- Partnership discussions with non-profits
- Official communications
- Updates to larger community

**Don't use for:**
- Day-to-day project work
- Technical discussions
- Urgent matters (use Slack)

## Working Together

### Inclusive Collaboration 🌈

**Everyone is welcome:**
- All skill levels from beginners to experts
- Technical and non-technical contributors
- Part-time volunteers and occasional contributors
- People from all backgrounds and identities

**How we ensure inclusivity:**
- Use clear, jargon-free language when possible
- Define acronyms and technical terms
- Be patient with questions
- Provide mentorship for new contributors
- Recognize different learning styles
- Acknowledge that English may not be everyone's first language

### Mentorship & Learning 🎓

**We believe in growing together:**
- Experienced members mentor newer contributors
- Everyone has something to teach and learn
- Mistakes are learning opportunities
- Ask questions - there are no dumb questions

**Mentorship opportunities:**
- Pair programming sessions
- Code review as teaching moment
- Tech talks and workshops
- AI/ML Mentorship Programme
- Project-specific onboarding

### Cross-Functional Collaboration 🤝

**Better.sg brings together:**
- Developers and designers
- Product managers and researchers
- Non-profits and government partners
- Students and working professionals

**How we collaborate across disciplines:**
- Respect different expertise areas
- Involve users and stakeholders early
- Share learnings across projects

## Code Review Culture

### For Authors 📝

**When submitting PRs:**
- Write a clear description of what and why
- Keep PRs focused and reasonably sized
- Add screenshots for UI changes
- Self-review before requesting review
- Respond to feedback promptly (within a week)
- Don't take feedback personally

### For Reviewers 👀

**When reviewing PRs:**
- Review within 2-3 days if possible
- Start with what's good
- Be specific and constructive
- Distinguish between "must fix" and "nice to have"
- Ask questions rather than make demands
- Approve when it's good enough, not perfect

**Review guidelines:**
- Check for security issues
- Verify tests are included
- Look for obvious bugs
- Consider maintainability
- Suggest improvements kindly
- Remember: it's about the code, not the person

## Conflict Resolution

### When disagreements happen:

1. **Assume good intent** - Everyone wants what's best for the project
2. **Focus on the problem, not the person** - Attack ideas, not people
3. **Seek to understand** - Ask questions before jumping to conclusions
4. **Look for common ground** - Find what you agree on first
5. **Escalate if needed** - Reach out to project leads or community managers

### Productive disagreement:

**Do:**
- "I see your point. Here's another perspective..."
- "Can you help me understand why you think that?"
- "What if we tried a hybrid approach?"
- "Let's prototype both and see what works better"

**Don't:**
- "That's obviously wrong"
- "We've always done it this way"
- "That won't work" (without explanation)
- Passive-aggressive comments or emojis

## Project Workflow

### Starting a new project:

1. **Define the problem** - What social issue are we addressing?
2. **Validate with users** - Talk to actual non-profits/communities
3. **Assemble the team** - Post in #general
4. **Set up infrastructure** - Repo, Slack channel, project board
5. **Create project README** - Goals, tech stack, how to contribute
6. **Break down work** - Create GitHub issues
7. **Start building** - In small, iterative increments

### Ongoing projects:

- **Weekly updates** - Project lead shares progress in Slack
- **Bi-weekly syncs** - Optional team check-ins
- **Monthly reviews** - What's working, what's not
- **Quarterly retrospectives** - Celebrate wins, learn from challenges

### When life happens:

**It's okay to:**
- Step back from a project
- Change your commitment level
- Take breaks
- Say no to new requests

**Just communicate:**
- Let the team know if you need to step back
- Unassign yourself from issues you can't complete
- Hand off work with documentation
- No explanation needed - "I need to step back" is enough
